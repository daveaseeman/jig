# roadmap

Source: owner, Nov 9: "I'd like to keep a roadmap in jig. Products, phases of work, and scopes
within phases." Then: product is the repo; a phase's exit criteria include "the scopes in that
phase are all marked as taken by specs that are completed"; "scopes and specs need not be 1:1";
no product spanning repos for now; "the repo is the source of truth". Then: changes come from
chat through staging, "kind of like it does with a user story"; instead of GitHub, a
`ROADMAP.md`; "We dont need dates … Could we maybe do something more like a kanban?"

## Intent
A repo keeps its roadmap in one file of phases and the scopes in each. Specs cite the scopes
they take, and jig works out each scope's and phase's state from the specs, so the roadmap
never needs a progress edit. jig renders it as a root `ROADMAP.md`, a kanban board per phase,
readable anywhere Markdown renders. A chat proposes roadmap changes through staging.

## Design
- **The source.** `.jig/roadmap.md`, optional. The product is the repo, so there is one
  roadmap per repo and no product level in the file. Phases are `## <phase>` headings, in
  order. Each has an `Exit when:` checklist and a `Scopes:` list:
  ```
  ## alpha
  Exit when:
  - [ ] boots on the dev board and draws a frame
  Scopes:
  - `screen`: the panel driver and a first frame
  - `battery`: charge state on screen
  ```
  A scope's id is `<phase>/<scope>` (`alpha/screen`). `Exit when:` holds only what the owner
  checks; "every scope is done" is implied, never written. No dates: phase order is file order.
- **Specs cite scopes.** A spec takes scopes with a `Scope:` line under `Source:`:
  `Scope: alpha/screen, alpha/battery`. Many-to-many: a spec may take several scopes, and a
  scope may be taken by several specs. A spec with no `Scope:` line (a bug fix, say) belongs
  to none. The spec template gains the line, and `/jig:spec` fills it from the roadmap or
  leaves it out.
- **A spec is complete** when a handoff note naming it (`Spec:`) is on trunk and its `Commit`
  is in trunk's history: its work landed, by `jig merge` or solo on trunk. A handoff for a
  chunk that doesn't finish its spec is written `jig handoff --partial` and records
  `Partial: yes`; a spec is complete at its first landed handoff without it.
- **Derived states.** A scope is *open* (no spec takes it), *taken* (some spec that takes it
  is not complete) or *done* (taken, and every spec that takes it is complete). A phase is
  *done* when every scope in it is done and every `Exit when:` box is ticked; the *current*
  phase is the first not done; the rest are *next*.
- **`jig roadmap`** prints the phases, their states and exit boxes, and each scope with its
  state and the specs that take it, all read from trunk. It also says when `ROADMAP.md` is
  stale.
- **The view: root `ROADMAP.md`**, generated, never edited by hand. Plain Markdown, so it
  renders on any forge, in an editor's preview, or as text; no Mermaid, whose kanban diagram
  is too new to count on being rendered.
  - A first line of phases in order with their state: `alpha ✓ → **beta** (current) → v1`.
  - Per phase, its exit boxes, then a board: a table with one column per state (Open, Taken,
    Done), each cell listing that phase's scopes in that state, every scope with its specs
    linked under it.
  - A header line saying it is generated by `jig roadmap --write` from `.jig/roadmap.md`.
  `jig merge` rewrites it in the merge commit, since that is when states change; `jig roadmap
  --write` rewrites it after solo work on trunk. Survey counts it as a home, not a stray.
- **The roadmap is the owner's.** R5 grows to cover `.jig/roadmap.md` and `ROADMAP.md`: both
  are edited on trunk only, like `config.json` and `jobs.json`. A phase or a scope is a
  decision, not work, and a branch regenerating the view would only make merge conflicts.
- **From chat: staging `kind: roadmap`.** A chat stages a file with `kind: roadmap`,
  `change: update`, `destination: .jig/roadmap.md`, whose body says what to add, rename,
  reorder or drop (a phase, a scope, an exit box) and why. Like a story, nothing in it is
  decided: the hubnode shows the owner the exact diff to `.jig/roadmap.md`, applies it on
  trunk on a yes, regenerates `ROADMAP.md`, and commits with the staged file's mark in the
  message. `jig staging resolve` finds that mark in the message of a trunk commit that changed
  `.jig/roadmap.md`, and refuses until it's there; the roadmap itself carries no provenance
  lines. A destination other than `.jig/roadmap.md` is refused.
- **Checks.** The commit hook refuses, reading trunk's roadmap:
  - a spec whose `Scope:` names a scope the roadmap doesn't have;
  - on trunk, a roadmap change that removes or renames a scope a spec on trunk still takes
    (the refusal names the specs, so they're re-pointed in the same commit);
  - `.jig/roadmap.md` or `ROADMAP.md` changed on a branch (R5).

## Done when
- [ ] Smoke `roadmap`, in a throwaway repo with a two-phase roadmap:
  - `jig roadmap` shows a scope no spec takes as open, one taken by a spec with no landed
    handoff as taken, and one whose specs all have landed handoffs as done;
  - a scope taken by two specs is done only once both are complete; one spec taking two
    scopes counts for both;
  - a landed `--partial` handoff leaves its spec incomplete; a later full one completes it;
  - a phase with every scope done but an unticked exit box isn't done; ticking it makes it
    done, and the current phase moves to the next.
- [ ] Smoke: `jig roadmap --write` writes `ROADMAP.md` with the phase line and a board per
  phase whose Open, Taken and Done cells hold the right scopes and link their specs; `jig
  merge` of a job whose spec takes a scope rewrites it in the merge commit, moving that scope
  to Done; `jig roadmap` reports a stale `ROADMAP.md`; survey doesn't list it as a stray.
- [ ] Smoke: the commit hook refuses a spec citing an unknown scope; refuses `.jig/roadmap.md`
  and `ROADMAP.md` edits on a branch; refuses a trunk roadmap edit that drops a scope a spec
  takes, naming the spec; accepts it when the spec is re-pointed in that commit.
- [ ] Smoke: a staged `kind: roadmap` file is listed by `jig staging`; resolve refuses before
  a trunk commit to `.jig/roadmap.md` carries its mark and lands after; a destination other
  than `.jig/roadmap.md` is refused.
- [ ] A repo with no `.jig/roadmap.md` is untouched: `jig roadmap` says there is none, `jig
  merge` writes no `ROADMAP.md`, and no hook check fires.
- [ ] RULES.md has a Roadmap section (the source, scopes, completion, states, the view, R5),
  Staging names `kind: roadmap`, and Commands lists `jig roadmap`.
- [ ] `bash tests/smoke.sh` passes, `claude plugin validate ./plugin` passes, and
  `grep -rnE 'Maige|maige|Daisy|daisy|"E-' plugin` finds nothing.

## Out of scope
- A product spanning repos. Each repo is its own product; adapt when that case is real.
- Dates, and any chart that needs them.
- Writing to GitHub, or reading from it. Any forge shows `ROADMAP.md` as it shows any file.
- Writing this repo's own roadmap. That's the owner's, after this lands.

## Alternatives considered
- GitHub as the home (Projects, milestones, labels) — rejected because jig keeps nothing
  platform-specific outside per-repo scripts, agents read the repo, not GitHub, and two homes
  drift — reason is [seen: owner, Nov 9]
- A GitHub Project pushed one way by a per-repo script (this spec's first draft) — rejected
  by the owner in favour of a `ROADMAP.md` in the repo — reason is [seen: owner, Nov 9]
- A Gantt chart — rejected because it needs dates, and phases have none — reason is [seen:
  owner, Nov 9, "We dont need dates"]
- Mermaid's kanban diagram — rejected because it's recent, and a forge on an older Mermaid
  shows a code block instead of the board; a Markdown table renders everywhere — reason is
  [assumed: GitHub's Mermaid version unchecked; the table works either way]
- Ticked Done-when boxes as completion — rejected because specs' boxes aren't maintained here,
  while a landed handoff is already recorded — reason is [seen: `.jig/specs/flatten-hardware.md`,
  merged with every box unticked]
- A `Status:` line in each spec — rejected because it's a progress edit someone must remember;
  the handoff already says the work landed — reason is [seen]
- Provenance lines in `.jig/roadmap.md` for staged changes, as an update to a doc carries its
  mark — rejected because they'd clutter the one file the owner reads as the plan; the commit
  message holds it, and git keeps history — reason is [seen: how `landed` checks a doc's mark,
  jig.py ~3900]

## Decisions
- Completion is a landed handoff, with `--partial` for a chunk that doesn't finish its spec.
- Scope ids are `<phase>/<scope>`, so the same name can recur in two phases.
- `ROADMAP.md` is regenerated at merge, not by the commit hook, so a solo handoff on trunk
  leaves it stale until `jig roadmap --write`; `jig roadmap` says so.
